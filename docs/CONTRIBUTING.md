# Contributing

[← Back to README](../README.md)

### Layout

| folder | what |
|---|---|
| `crates/wipe-core` | combat log parser and pull analysis (Rust, no UI dependency) |
| `src-tauri` | desktop app (Tauri) exposing `wipe-core` to the UI |
| `src` | interface (React + TypeScript) |
| `crates/wipe-wasm` | the core compiled to WebAssembly for the web version (bindings in `src/web/pkg`, built by `npm run wasm`; the web backend is `src/web/`) |
| `encounters/` | per-boss rules (YAML), generated by the `boss-rules` skill; what each ability draws on the replay comes from the `replay-build` skill |
| `rotations/` | base rotation per spec (YAML), kept up to date by `npm run refresh` and the `rotation-refresh` skill |
| `src/lib/simProfile.ts` | the fight model the SimulationCraft bot plays, checked per boss by `npm run sim:check` and the `sim-calibrate` skill |
| `data/` | editable tables: defensives per class, consumables, interrupts, player utility such as CC (`utility.json`) and the boss arenas (`arenas.json`) |
| `docs/screenshots/` | screenshots and animated clips of the README and the user guide (`pt/` and `en/`) |
| [`docs/designs/`](designs/SITEMAP.md) | design docs for big features (in Portuguese), indexed in `SITEMAP.md` |
| [`docs/APP-MAP.pt-BR.md`](APP-MAP.pt-BR.md) | map of the screens and how they connect (in Portuguese) |

### Development

Requirements: Node 22.12+ (Vite and Vitest require it; `npm run refresh` uses `--experimental-strip-types`), Rust (rustup) and MSVC Build Tools (Windows).

```bash
npm install
npm run tauri dev
```

Run only the analyzer, with no UI:

```bash
cargo run -p wipe-core --bin wipe-cli -- analyze path/to/WoWCombatLog.txt
```

`wipe-cli` subcommands (the scripts use the release build, `cargo build --release -p wipe-core --bin wipe-cli`, in `target/release/`):

- `analyze <file> [--json] [--cutoff N] [--tuning <folder>]`: the pulls, or the full report as JSON; `--cutoff N` ignores events after N deaths; `--tuning` applies the user's rule adjustments (`<encounter_id>.json`). `--cutoff` also works with `wcl`, `spells` and `fight`, and `--tuning` with `spells` and `fight` (in `wcl`, only on the `--local` pulls).
- `spells <file>`: enemy spells per pull, as CSV (encounter, spell, casts, hits, damage), to calibrate boss rules.
- `rules`: the built-in boss rules, as JSON.
- `peek <file>`: only the log's encounters (quick read).
- `positions <file>`: where the players stood on each boss, to align an arena image.
- `radius <file> --damage <id> (--aura <id> | --npc <id> | --soak)`: the radius of an area.
- `wcl <folder>[,<folder>] [--json] [--local <log>]`: analyzes reports downloaded from Warcraft Logs (`scripts/wcl-fetch.mjs`); `WIPE_TZ` sets their time zone (default -3).
- `fight <file> --pull <id>`: one pull's full replay.

Web version (the same core in WebAssembly, published on GitHub Pages):

```bash
rustup target add wasm32-unknown-unknown
cargo install wasm-bindgen-cli --version 0.2.129 --locked
npm run wasm
npm run dev:web
```

`npm run wasm` builds `crates/wipe-wasm` into `src/web/pkg`; `npm run build:web` builds the site.

To test live mode without raiding: `node scripts/simulate-live.mjs <old log> <Logs folder> [pulls=3] [seconds per pull=8]` writes a few pulls from a real log, bit by bit, into a new `WoWCombatLog`.

Other development tools:

| Command | What |
|---|---|
| `npm test` | Vitest tests (interface, language guards, scripts) |

Development environment variables: `WIPE_DEV_SIMC_EXE` (the SimulationCraft the Vite dev bridge runs), `WIPE_DEV_VIDEO_DIR` (videos served in development), `WIPE_GAZE_DUMP` (dumps the ghosts' data for `scripts/ghost-calibrate.mjs`) and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` (the signing key's password, if it has one).

GitHub workflows: `ci.yml` (tests, clippy and builds, on every PR and push to `main`), `pages.yml` (publishes the web version, on push to `main` or by hand) and `simc.yml` (builds the SimulationCraft the app downloads, weekly and by hand; a PR that changes `simc.yml` only builds it).

### Texts in both languages

Every new text goes in Portuguese and English in the same change.

- **Interface:** texts live in dictionaries (`*.i18n.ts` or `*.i18n.tsx`, with `defineMessages(pt, en)`; `src/i18n/` too); English is typed against Portuguese, so a missing phrase doesn't compile. One test fails if Portuguese shows up outside the dictionaries, another if a dictionary's English side has Portuguese in it, and a third if a Rust string has Portuguese outside `pick()`, `tx!` or `Text` (hand-written pt/en pairs get `i18n-ignore` on the line).
- **Boss rules and rotations (YAML):** tips, messages, titles and notes are `{ pt: "...", en: "..." }`; names stay in English. The `wipe-core` test checks both.
- **Release notes:** a `## Português` section and a `## English` section (the app shows the one for the chosen language).

### Project rules

Rules that decide how a feature is designed in this project.

1. **A boss is data, not code.** What a boss shows or checks comes from its rule (`encounters/`) or from `data/*.json`. A boss that needs something new gets a generic field, designed with other bosses in mind, through the [Feature workflow](#feature-workflow) (criterion b); never an `if` for one boss. Details: [replay-methods.md](replay-methods.md) (in Portuguese), principle 1.
2. **The healer reference comes from outside the guild.** Healer analysis compares only with other guilds' logs. Our raid's logs are never the "right" answer: not a teammate of the same spec, not the player's own earlier kill, not for calibrating targets. Fight parameters, such as the hit and the low raid of the [healing CD note](heal-cd-note.md), measure the boss, not the healer, and may be calibrated on our logs (decision of 2026-10-27). Details: [healer-analysis.md](healer-analysis.md) (in Portuguese).
3. **Release only with an approved feature.** A version and a release come out only after the developer approves the feature. Details: "Versions and automatic updates" block.
4. **A boss or spec piece is a standard process:** a script does the numbers and, except for boss rules, writes an OK / ATENÇÃO / REVISAR report; a skill handles the REVISAR items. Details: [Standard processes](#standard-processes).
5. **Interface.** Every ability shows with its icon and name (icon alone only where text does not fit, with the name in the tooltip). Every boss shows with the boss icon. Every character shows in the class color, also inside sentences. Cards, lists and notices have no colored stripe or border on the side or top; a selected item changes only its background. Exception: Discord text messages.
6. **The replay shows the boss abilities.** Frontals as cones, things on the ground, areas around whoever carries something or around a boss unit, lines, soaks, explosions, orbs and adds always show on the map, on top of the boss arena. Details: [replay-methods.md](replay-methods.md) (in Portuguese).

### Feature workflow

A request goes through EGM when it meets at least one of these:

- **(a)** it changes the core (`crates/` or `src-tauri/`) and the interface (`src/`) in the same change;
- **(b)** it creates a new kind of field or check in `encounters/`, `rotations/` or `data/*.json`;
- **(c)** it brings a new external integration (a service, program or file format the app does not read yet).

Left out, even if they meet (a): a bug fix with a known cause, and boss or spec content that only uses fields that already exist (those go through the standard processes). Also left out: text-only changes (docs or interface phrases) and visual-only changes that create no screen or component. When in doubt, the session asks the developer.

A big feature has a design in `docs/designs/` (index in [SITEMAP.md](designs/SITEMAP.md), in Portuguese), with Status Approved, inside the feature's PR and cited in the PR description. It can be written by hand, following the template in the SITEMAP, or with the EGM plugin (`egm@egm`).

Before a minor release: `npm run docs:links` exits with 0, and the doc check from [the EGM design](designs/egm-adoption.md) (in Portuguese) runs on CONTRIBUTING, the APP-MAP and the rule docs, plus any doc changed since the last minor tag.

### Standard processes

Each piece of a boss and of a spec has its own process: a script does what is numbers (no AI) and writes a report with **OK**, **ATENÇÃO** (attention) or **REVISAR** (review); a Claude Code skill handles the REVISAR items. Boss rules are the exception: `wipe-cli spells` (CSV) and `wipe-cli radius` (histogram) give the numbers without a status, and the boss's status report comes from `replay:check`.

| What | Numbers | REVISAR |
|---|---|---|
| Boss rules (what is a mistake, who is blamed) | `wipe-cli spells` / `wipe-cli radius` | `boss-rules` skill |
| Boss replay (abilities on the map, arena) | `npm run replay:check` | `replay-build` skill |
| Spec rotation | `npm run refresh` | `rotation-refresh` skill |
| Boss simulation (the SimulationCraft bot) | `npm run sim:check` | `sim-calibrate` skill |

A new boss goes through the first two and the last; a patch or a new raid, through `refresh` too.

<details>
<summary><b>Updating everything after a patch, a new raid or a nerf</b></summary>

`npm run refresh` redoes, without AI, everything that changes with the game: it downloads SimulationCraft's APL (and flags the specs where it changed), runs each spec's tops through the engine, adjusts only the rotations' numbers (uptime and cooldown usage targets from the tops' lower quartile; a new id for the same ability in `alt_ids`; a repeated event of the same button in `ignore_casts`), generates the tops' per-boss reference and writes a report to `samples/refresh/<date>.md` (and `.json`; a run on some specs writes `<date>-<specs>.md`) with each spec **OK**, **ATENÇÃO** (attention) or **REVISAR** (review).

- `npm run refresh -- --tops`: downloads the tops first (credentials from environment variables, `samples/wcl-credentials.env`, kept out of git, or the app's vault; with more than one client in the file, it switches when the hourly points run out).
- `npm run refresh -- --tops --zone latest --fresh`: a new raid; the bosses come from Warcraft Logs' newest zone (no written rules needed) and the previous raid's tops leave the reference. `--zone` also takes a zone id; `--fresh` renames each old tops folder to `tops-<date>`, deleting nothing.
- `npm run refresh -- arcane fire`: only those specs (without names, every spec with a YAML in `rotations/`).
- `npm run refresh -- --tops --per-boss N`: tops to download per boss (default 4).
- `npm run refresh -- --dry`: just the report, without changing YAMLs or the reference (the SimulationCraft APL cache is still updated, so the next run no longer flags "APL changed"); can be combined with spec names.

REVISAR is what changes what the spec is (an ability the tops stopped using, a new ability, a new APL, a check not even the tops meet): Claude Code's `rotation-refresh` skill handles it.

</details>

<details>
<summary><b>Generating a spec's rotation</b></summary>

No handwriting and no AI: `scripts/rotation.mjs` builds the YAML from SimulationCraft's APL and spell data and calibrates it on the Warcraft Logs tops' logs.

1. `node scripts/rotation.mjs tops <spec> [--difficulty 5] [--per-boss 2]`: downloads the 2 best parses of each raid boss (a fight with someone else's Power Infusion is dropped), with the player's and pets' events, the buffs on them, deaths, enemy casts and one teammate's damage, to `samples/rotation/<spec>/tops/`. Credentials as in `refresh`: environment variables, `samples/wcl-credentials.env` or the app's vault.
2. `node scripts/rotation.mjs calibrate <spec> [--dirs a,b] [--force]`: generates the draft and runs it on the tops with the app's own engine.
   - **Priority:** from the APL, per hero tree, for single target and AoE.
   - **Ids:** from what the tops cast.
   - **Numbers:** cooldown, charges and cast time come from the SimC dump (or Wowhead's tooltip).
   - **Inferred checks:** DoT, from `dot.X.refreshable`; proc, from `buff.X.react` on a spell the buff modifies; resource, from the spenders' cost; cooldowns of 20s or more (or 15s or more with more than one charge).
   - **Calibration from the tops:** uptime and cooldown usage targets from what the tops do; the opener, from what 70% of them cast in the first seconds; drops what not even the tops meet.
   - **Output:** written to `rotations/`; if a handwritten one already exists, it goes to `samples/rotation/<spec>/` for comparison, unless `--force`.
3. `node scripts/rotation.mjs check <spec> [--dirs a,b] [--opener]`: shows how the tops do on the current rotation, to validate a handwritten one.

Also: `node scripts/rotation.mjs gen <spec> [--dirs a,b] [--force]` (only the draft, with the previous calibration) and `node scripts/rotation.mjs refs <spec> [--per-boss 4]` (healers: reference logs; rules in [healer-analysis.md](healer-analysis.md), in Portuguese). `--dirs` takes folders in the `scripts/wcl-fetch.mjs` format instead of the downloaded tops; `--build` rebuilds `wipe-cli` first; `<spec>` can be `unholy`, `deathknight-unholy` or the id (252). After `refs`, `node --experimental-strip-types scripts/rotation/heal-bench.mjs [spec ...]` writes `src/data/heal-refs/<spec>.json`, the healer reference the app reads. At the end it checks the healing CD table (`data/heal-cooldowns.json`, used by the [healing CD note](heal-cd-note.md)) against the references and the spec rotation: a CD heal that no reference has is ATTENTION; a rotation ability with a 60 s or longer cooldown, cast by the references and missing from the table, is REVIEW (an entry without `kind` marks it as known and not a raid CD; the `rotation-refresh` skill fills the rest).

Check types: `proc` (a buff that must be spent, charge by charge — e.g. Precise Shots, Demonic Core), `requires_buff` (casts that need a buff — e.g. Trick Shots, Demonbolt with Demonic Core), `downtime` (time without casting, only while the raid was hitting), `cooldown` (uses vs. possible over the time alive), `resource_waste` (capped resource, e.g. Maelstrom, Astral Power, Soul Shards), `dot_uptime` (DoT on the target, e.g. Flame Shock), `aoe_swap` (with N+ targets the cast should be another, e.g. Chain Lightning), `ally_uptime` (healers: the player's buff kept on raid members, e.g. Beacon of Light, with an uptime or a number-of-targets goal) and `after_cast` (a cast that must come right before or after another, e.g. Demonic Tyrant with the Dreadstalkers out).

The texts come out as templates ("X wasted: use it before it expires"), in both languages: review the key points before publishing.

</details>

<details>
<summary><b>Building a boss's replay</b></summary>

[Project rule 6](#project-rules): the boss's abilities always show on the replay (frontals as cones, things on the ground, areas around whoever carries something or around a boss unit, lines, soaks, explosions, orbs, adds) on top of the boss's arena (raidplan.io image aligned with the log's coordinates, `data/arenas.json`).

`npm run replay:check -- <WoWCombatLog.txt | report.json> [--boss "<name>"] [--difficulty Mythic]` (without them, the boss and difficulty with the most pulls) crosses the log with the boss rule and the arena and writes `samples/replay/<date>-<boss>-<difficulty>.md` (and `.json`): each enemy ability that hit players, the rule it is in and what it draws; the boss's casts no rule knows (frontals and lines often start there); units that deal damage and are not on the map; missing arena or a poor fit. Needs `wipe-cli` built in release.

REVISAR is a shape or a rule to write: Claude Code's `replay-build` skill handles it (shapes, measuring sizes with `wipe-cli radius`, the arena with `scripts/arena-fit.mjs`, the ghosts with `scripts/ghost-calibrate.mjs`). Example audit: [docs/coiled-altar-replay-audit.md](coiled-altar-replay-audit.md) (in Portuguese). Method: [docs/replay-methods.md](replay-methods.md) (in Portuguese). Another audit: [docs/twin-fangs-vashnik-replay-audit.md](twin-fangs-vashnik-replay-audit.md) (in Portuguese).

</details>

<details>
<summary><b>Configuring a boss's simulation (the SimulationCraft bot)</b></summary>

The bot plays **the fight model**, taken from the log. Each player is simulated on their own pull of that boss and difficulty on the same night (a kill they survived → a kill → the longest pull without dying → the most time alive); inside a pull, the model is the same for everyone: how much the fight made people move (every 30s, the bottom quarter of the DPS by how much they moved), targets and adds, time without a target, health per phase (so the bot spends as long in execute as the fight did) and Bloodlust/Power Infusion at the same moments. Nothing is written by hand per boss; what decides it is the log and the boss rules (`phases` in `encounters/`).

`npm run sim:check -- <WoWCombatLog.txt | report.json> [--boss "<name>"] [--difficulty Mythic] [--iterations 1000] [--cutoff 4]` simulates the raid's DPS and tanks on that boss (healers are left out) with the app's own code, compares it with what each player did and writes `samples/sim/<date>-<boss>-<difficulty>.md` (and `.json`) with **OK**, **ATENÇÃO** or **REVISAR**: the DPS median (without tanks and Augmentation) outside 85–105% of the bot (the fight model is too easy or too hard), a DPS above 110% (the bot is weak for that spec: adds, execute or the spec's APL), a profile SimulationCraft did not run, a profile without the measured movement (an old `wipe-cli`); ATENÇÃO for a DPS below 70% of the bot. Needs `wipe-cli` built in release and the app's SimulationCraft (or `WIPE_SIMC_EXE`).

REVISAR is what changes the fight model (a measurement in the core, the boss's phases, a model constant): Claude Code's `sim-calibrate` skill handles it. The full rules are in [docs/simulation.md](simulation.md) (in Portuguese).

</details>

<details>
<summary><b>Versions and automatic updates</b></summary>

Versions follow semver. Each big feature is closed in a release (`vX.Y.Z`) after it's approved.

The installed app looks for a new version when it opens (and every 6h): it reads the `latest.json` of the latest GitHub release and shows a banner; on **Update and restart**, it downloads the installer, verifies the signature and reinstalls itself (in development it doesn't check). In the sidebar or in Settings, "Check for updates" forces the check.

Publishing a version:

1. For a minor version, first run the checks in [Feature workflow](#feature-workflow).
2. Bump the version in `Cargo.toml`, `package.json` and `src-tauri/tauri.conf.json`, then `npm install` to update `package-lock.json`.
3. `npm run release:build` — a build signed with the private key in `~/.tauri/wipe-cause.key` (or in `TAURI_SIGNING_PRIVATE_KEY`, if set; outside the repo; without it you can't publish updates, keep a backup).
4. `node scripts/release.mjs docs/releases/vX.Y.Z.md` (with `## Português` and `## English` sections) — generates `target/release/upload/` with the installer (with the version in the name and a `WipeCause_x64-setup.exe` copy, which is the README's download link) and `latest.json`, and prints the `gh release create` command to publish all three.

</details>
